## 一、本次已修复

1. **手动刷新静默失败无反馈（真正根因）**：在 `include:web-search-pool` 这类 loader/include
   装配下，`installSettingsSection` 注册的 `scope.watch` 存在但没有触发插件 `onChange`，
   所以 `usageRefreshTick` 能写入、Host 却不刷新。修复为在插件入口同时监听 `settings/updated`
   事件，直接用事件 `next` 快照触发 `refreshUsage`，不依赖 scope.watch。Host `refreshUsage()`
   同时增加 15 秒总超时；每个 key 的查询失败/未配置凭据会聚合进 `usageDiagnostic`；
   `writeUsage` 改为一次 `settings.update` 同时写 `usage` 与 `usageDiagnostic`，
   失败再单独写诊断兜底。
2. **Client 吞错且无提示**：`refreshUsage()` 不再用空 catch；mutate 成功显示
   “已请求刷新，等待 Host 回写”，失败显示“刷新请求失败：…”，按钮等待 5 秒恢复。
3. **手动刷新后未立即解除长冷却**：`refreshUsage()` 更新额度缓存后调用 `_recoverQuota()`，
   已恢复的 key 不需要等下一次搜索才解除冷却。
4. **`timeRange: off` 未禁用 `days`**：query 含“最近 N 天”时，`off` 仍会把 `days`
   发给 Tavily；已修复并补测试。
5. **空 Tavily key 时刷新无反馈**：无 Tavily key 时也会发布带诊断的空快照，避免 UI 无变化。

## 二、仍存在的问题与优化建议

### P1（建议尽快处理）

- **Client 保存是多次 `scope.set`**：`save()` 对多个字段连续写入 settings，每次独立提交并携带
  revision，可能触发多次 `onChange` 或中途 revision 冲突。官方 settings 卡片是暂存表单、
  保存时单次写入。建议改为一次 `api.settings.update`（或 `scope.update`）提交整个补丁。
- **手动刷新防重入**：当前 Client 有 5 秒按钮防连点，但 Host 手动刷新没有复用
  `_usageRefreshPromise`，快速请求仍可能并发查询 Tavily。建议手动刷新也走统一 in-flight promise。

### P2（低风险/体验优化）

- **`refreshUsage()` 不等待 settings 发布完成**：正常路径够用，但若用户刷新后立刻关闭 DSH，
  最后一次 usage 写入可能未落盘。手动路径可考虑 await 发布，自动搜索路径保持不阻塞。
- **Client 定时器未清理**：刷新提示与按钮恢复使用 `window.setTimeout`，建议用 `useRef` 保存并在
  组件卸载时清理。
- **`_search()` 在 `_ensureUsage()` 后仍持有旧 pool 引用**：若刷新期间配置变化导致 `_getPool()`
  重建，`_search()` 后续可能使用旧 pool；极端场景下建议刷新后重新取 pool。
- **`TokenBucketLimiter.reset()` 用 `Date.now()`**：与 Scheduler 注入时钟不一致，测试/运维时可能
  不准；可改为传入时间源。
- **`KeyPool.isTripped()` 与 `isCooling()` 等价且未使用**：属死代码，可删除。
- **`scripts/patch-api-proxy-namespace.mjs` 用字符串锚点定位白名单**：当前白名单结构稳定时幂等；
  若 DSH 升级改变格式或注释出现同名字符串，可能 patch 错位。建议后续改为解析数组或加上下文校验。
- **Exa 匿名 MCP 只解析 SSE 第一行 `data:`**：已实测托管 MCP 可用；若上游改成多行 JSON/非 SSE，
  解析会失败。建议后续引入标准 SSE 解析器。
- **`available()` 不检查凭据是否真实可解析**：符合官方“本地可用性检查，不发网络”的契约；
  但凭据缺失会延迟到搜索时报错。可在本地 `credentials.describe` 可获取时做轻量检查。

## 三、机制合规性确认

- Host 取 settings 服务使用 `ctx.inject(['settings'])`，未依赖不稳定的 `ctx.get` 路径。
- Client 手动刷新使用 `api.settings.mutate` 且不带 `expectedRevision`，符合事故三教训。
- 可观测性只写 `ctx.logger`，未写未注册会话事件。
- ESM 入口内部使用 `SearchPoolProvider` / `SEARCH_POOL_PROVIDER_ID` 均显式 `import`。
- 核心调度库不依赖 DSH，保留未来多实例/HTTP 外壳升级路径。

### 5.1 稳定性修复

| # | 问题 | 修复 |
|---|------|------|
| 1 | **搜索请求无 per-attempt 超时**：上游挂起时 `search()` 永久 pending | 新增 `requestTimeoutMs` 配置（默认 20s，0 禁用）；`core/http-utils.js` 的 `withTimeout` 组合外部 signal 与内部定时器（Node 18 兼容，不用 `AbortSignal.any`）；超时按 key 失败处理并换 key（`TIMEOUT` 观测码），与外部用户取消严格区分 |
| 2 | **`_ensureUsage` 阻塞搜索首字节**（缓存过期时最长等 15s） | 额度刷新完全后台化：搜索只读缓存，过期/无缓存时单飞 fire-and-forget 刷新；本轮闸门用旧数据，无缓存先放行、上游错误兜底；`_recoverQuota` 移入刷新完成回调 |
| 3 | `resolveKey` 在 try 外，抛错炸整个搜索且令牌白扣 | 包进 try：非 abort 异常 → `recordError` + `KEY_RESOLVE_FAILED` 观测 + 换 key |
| 4 | `lastSyncedEnabled` 是模块级可变状态（多实例/热重载竞态） | 移入 `apply` 闭包；`syncSearchProvider` 一并移入 |
| 5 | apply 无清理（事件监听/provider 状态残留） | apply 返回 dispose：`ctx.off('settings/updated')` + `provider.dispose()`；disposed 后 `available()` 为 false、`search()` 抛 `WEB_PROVIDER_UNAVAILABLE` |
| 6 | 手动刷新无防重入（P1） | `refreshUsage` 本身单飞（`_usageRefreshPromise` 复用），覆盖后台与手动两条路径 |
| 7 | `lastError` 为 `RateLimitError` 时被外层包成 `WEB_PROVIDER_ERROR` 丢失语义（P2） | 循环耗尽时显式转 WebError 且 message 携带 retry-after 信息 |
| 8 | 429/非 OK 响应体不消费（undici 连接积压） | `discardBody(response)` 防御式清理（tavily/exa 全部分支） |
| 9 | pool 重建与 in-flight 刷新的弱竞态 | `_performUsageRefresh` 写回缓存前比对 pool 引用（`_poolCache === pool`） |
| 10 | Client 3 处 `setTimeout` 不清理 + `describeCredentials` 竞态（P2） | `setLater` + 卸载统一清理；序号守卫丢弃过期凭据响应；catch 写 `console.warn` 不再静默 |

### 5.2 效率优化

| # | 位置 | 优化 |
|---|------|------|
| 1 | `provider._getPool` | 每次 `JSON.stringify(entries)`×2 的缓存键 → `samePoolOptions` 浅比较（O(n) 无序列化）；同引用直接命中 |
| 2 | `key-pool.js` | `entryById` O(n) find → 构造时 `Map<id>` / `Map<credentialRef>` / `Map<provider>` 三组索引，全部 O(1)；`entriesForProvider` 不再每次 filter |
| 3 | `scheduler.js` | WRR 与 least-used 的 `[...candidates].sort()` → 单遍选最大值 `_acquireByRank`（无数组复制与排序分配，行为等价：相等取先出现者） |
| 4 | `refreshUsage` | 串行逐 key 查 `/usage` → `Promise.all` 并行（保留 15s 总超时与逐 key 错误收集），多 key 快 N 倍 |
| 5 | `_recoverQuota` | `entries.find` O(n) → `keyPool.entryByRef` O(1) |
| 6 | `client.js save()` | 9 次连续 `scope.set` → 1 次 `api.settings.mutate` 多 op 事务提交（无 api 时回退原链路），消除多次 revision 冲突面与多次广播（P1） |
| 7 | `check-usage.mjs` | O(n²) 全文重扫 → 一次扫描建 Map |
