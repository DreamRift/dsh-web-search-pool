# DSH 搜索池插件开发事故复盘与规范

> 记录 `dsh-web-search-pool` 开发过程中造成的四次事故：原因、修复与后续预防。
> 日期：2026-08-15。适用版本：DeepSeek Harness `0.1.0-rc.6`。

## 事故一：`SEARCH_POOL_PROVIDER_ID is not defined` 启动报错

### 现象

启动 `dsh web` 时插件树加载失败：

```text
dsh: plugin tree failed to load: failed to apply loader entry web-search-pool (dsh-web-search-pool):
SEARCH_POOL_PROVIDER_ID is not defined
ReferenceError: SEARCH_POOL_PROVIDER_ID is not defined
```

### 根因

`src/dsh/index.js` 同时存在两种写法：

```js
// 这行只是 re-export，不会在当前模块创建局部绑定：
export { SearchPoolProvider, SEARCH_POOL_PROVIDER_ID } from './provider.js';
// 但当前模块内部直接使用了该名字：
const providerId = enabled ? SEARCH_POOL_PROVIDER_ID : 'deepseek-official';
```

`export ... from ...` 只把名字转发给外部，**不会**在当前模块建立可用的局部绑定；ESM 里内部使用必须先 `import`。于是 `apply()` 执行到该表达式时抛 `ReferenceError`。

### 修复

```js
import { SearchPoolProvider, SEARCH_POOL_PROVIDER_ID } from './provider.js';

export { Config, resolveOptions } from './config.js';
export { SearchPoolProvider, SEARCH_POOL_PROVIDER_ID };
```

### 教训

- 模块内部要用的常量/函数必须显式 `import`。
- `export { x } from './y.js'` 与 `import { x } from './y.js'` 是两个不同绑定，不能混用直觉。
- 改完入口文件后至少做一次 `node --check`，并实际重启验证 `apply`。

## 事故二：会话历史加载失败（自定义会话事件不兼容）

### 现象

会话重启后历史无法加载：

```text
历史加载失败：history unavailable for session "...":
SessionFormatUnsupportedError:
session "..." contains event type "web/search-pool-attempt" (seq 15406)
unknown to this harness and not marked ignorable;
refusing to interpret the log
```

### 根因

插件为了可观测性，在 `src/dsh/config.js` 向会话日志写自定义事件：

```js
ctx.get('agents')?.currentInitiator()?.session.append('web/search-pool-attempt', record);
```

而 DSH `0.1.0-rc.6` 的会话事件词汇是固定集合：

- `@deepseek-ai/dsh-session/lib/types/known-event-types.js` 的 `KNOWN_SESSION_EVENT_TYPES`
- 不含 `web/search-pool-attempt`

读取端（`@deepseek-ai/dsh-session-persistence`）遇到「未知且未标记 `ignorable: true`」的事件会直接拒绝整个会话日志，防止未知事件影响会话重建时静默丢数据。且 rc.6 的 `Session.append` 未开放 `ignorable` 参数，插件无法从 API 标记。

### 修复

1. 对受影响日志中 8 条 `web/search-pool-attempt` 事件补 `"ignorable": true`，重新压缩为 zstd JSONL，恢复会话加载。
2. 后续又发现两个会话受影响（各 4 条、2 条），同样补 `"ignorable": true`，
   并把 `web/search-pool-attempt` 补入 DSH 会话事件目录（`dsh-session` 的 `known-event-types.js`/`index.js`/`types.d.ts`）。
3. 修改插件 `recordRequest`，不再写会话事件，改用插件日志：

```js
recordRequest: (record) => {
  ctx.logger?.info?.(`search-pool attempt ${JSON.stringify(record)}`);
},
```

### 教训

- **不要向会话日志写入核心不认识的未注册事件**；核心版本升级前，会话事件词汇不可扩展。
- 需要可观测性时，优先 `ctx.logger`；若必须写会话事件，先查 `KNOWN_SESSION_EVENT_TYPES` 且确认 API 支持 `ignorable`。
- 涉及会话/持久化格式的操作要格外谨慎，破坏历史加载影响最大。

## 事故三：额度总览不更新（运行时状态发布静默失败）

### 现象

设置页「Tavily 额度总览」显示默认值（已用 0 / 可用 — / 上限 — / 更新 等待刷新）；
点击「立即刷新」后 `usageRefreshTick` 已递增，但 `usage.updatedAt` 不变，也没有错误提示。

### 根因

1. Host 端发布额度快照时使用 `ctx.get('settings')`，在该插件上下文里可能拿不到 settings 服务，
   发布函数静默 `return`，额度快照从不写回 settings。
2. Client 端「立即刷新」用 `settingsScope.set` 写入 `usageRefreshTick`，会带 `expectedRevision`；
   Host 刚写完 usage 时 revision 已前进，客户端写入发生 `SettingsConflictError`，tick 写不进去，
   Host 的 `onChange` 不会触发，表现为点击无反应。
3. 排查阶段还发现：只刷新浏览器页面不会加载新的 Host/client.js，必须重启 DSH 进程。

### 修复

1. Host 发布改经 `ctx.inject(['settings'])` 获取 settings 服务，并在服务未就绪时把快照存到
   `pendingUsage`，服务出现后补发；发布失败写入 `usageDiagnostic` 供设置页显示。
2. Client「立即刷新」改用 `api.settings.mutate` 且不传 `expectedRevision`，避免 revision 冲突。
3. 文档明确：改 Host/client.js 后必须重启 DSH 进程验证，不能只刷新浏览器。

### 教训

- Host 插件取共享服务优先用 `ctx.inject`，不要依赖 `ctx.get` 在任意上下文中可用。
- 把运行时状态写进 settings namespace 是可行的 Host→Client 通道，但要注意 revision-fenced 写入冲突。
- 客户端显式写入若不需要乐观并发，可用无 `expectedRevision` 的 mutate，保证请求一定到达 Host。
- 排查「UI 没反应」先区分 Host 数据是否更新、Client 是否加载了新代码，不要只盯着前端。

## 事故四：额度刷新静默无反馈（点击后 usage 不更新且无提示）

### 现象

设置页「Tavily 额度总览」更新时间不变；点击「立即刷新」后 `usageRefreshTick` 已递增，
但 `usage.updatedAt` 不变，也没有诊断/错误提示，用户不知道刷新是否发生。

### 根因

1. **真正根因：`installSettingsSection` 的 `scope.watch` 已注册但不触发插件刷新。**
   在 `include:web-search-pool` 这类 loader/include 装配下，`usageRefreshTick` 每次都能写入
   settings，revision 也递增，但插件 `onChange` 没有执行；`provider._usageCache` 一直为 null。
   运行时用宿主内调试工具确认：`settings/updated` 事件和自定义 watcher 都能收到变更，
   而插件原 watcher 回调没有产生任何刷新。
2. Host `refreshUsage()` 对每个 key 的查询失败只写插件日志，不写 `usageDiagnostic`；
   若查询挂起或发布失败，设置页完全不知道。
3. `writeUsage()` 先写 `usage` 再写 `usageDiagnostic`，不是一次写入；失败路径可能连诊断也丢失。
4. Client `refreshUsage()` 对 `api.settings.mutate` 的 rejection 用空 `.catch(function () {})` 吞掉，
   且 1.2 秒后强制结束“刷新中”，用户看不到请求是否发出。
5. 顺带发现 `resolveTavilyParams` 的 `timeRange: off` 只禁了 `time_range`，query 里的“最近 N 天”
   仍会变成 Tavily `days`，`off` 语义不完整。

### 修复

1. **插件入口同时监听 `settings/updated` 事件**，用事件 `next` 快照直接触发 `refreshUsage`，
   不依赖已失效的 `scope.watch` 回调。
2. `refreshUsage` 聚合每个 key 的失败/超时，构造诊断并随 snapshot 一次写入 `usageDiagnostic`；
   单次刷新加 15 秒 `AbortController` 超时，避免网络挂起。
3. `writeUsage(snapshot, diagnostic)` 一次 `settings.update` 写 `usage` + `usageDiagnostic`，
   发布失败再单独写诊断兜底。
4. Client 不再吞错：mutate 成功显示“已请求刷新，等待 Host 回写”，失败显示“刷新请求失败：…”，
   按钮等待 5 秒恢复。
5. `resolveTavilyParams` 在 `timeRange: off` 时同时禁用 `days`，并补测试。

### 教训

- `installSettingsSection` 的 `scope.watch` 在 include/loader 场景下可能已注册但不触发；
  对“设置变化必须驱动 Host 动作”的强要求，应再加 `settings/updated` 事件兜底。
- 用户可点击的“刷新”必须有可见结果：成功至少更新时间，失败必须写诊断或显示错误，不能只写日志。
- 网络类运行时刷新必须带超时，避免 Host promise 永久挂起造成 UI 永远无反馈。
- 诊断和业务数据应尽量同一 settings write，避免“半成功”状态。

## 后续预防规范（DSH 插件开发检查清单）

1. **ESM 绑定**：入口文件内部使用的符号必须 `import`；`export { x } from ...` 不产生局部绑定。
2. **会话事件**：禁止 `session.append` 写未注册且未标记 `ignorable` 的自定义事件；观测优先用 `ctx.logger`。
3. **DSH 机制先查源码**：涉及 seam / settings / api-proxy / session 的结论，先读已安装源码确认，不要凭印象写（如 settings 暴露必须进 `WEB_SETTINGS_NAMESPACES` 白名单）。
4. **改动后必验证**：`node --check` 语法检查 + 实际重启验证 `apply` 不报错。
5. **不直接改 npm 安装目录**：若必须 patch 官方包（如 api-proxy 白名单），做成可重复脚本（见 `scripts/patch-api-proxy-namespace.mjs`），升级后重跑。
6. **真实 key / 配置**：搜索池需要真实 Tavily/Exa key，填入 `$DSH_HOME/.credentials.yaml` 或启动环境变量后才可真实搜索。
7. **客户端密钥写入顺序**：凭据必须 `await api.credentials.set` 成功后再提交 settings，保存后重新 `credentials.describe` 刷新徽标，避免“设置已保存但凭据未配置”。实现参照官方 `dsh-client-ui-settings-plugins` 的 `SecretField`/`CardForm.save`（0.1.0-rc.6 已安装源码）。
8. **运行时状态发布通道**：Host 取 settings 服务用 `ctx.inject`；发布失败要写 `usageDiagnostic` 之类可见诊断；客户端显式触发用无 `expectedRevision` 的 mutate，避免 revision 冲突静默失败。
9. **改 Host/client.js 必须重启 DSH 进程**：仅刷新浏览器不会加载 out-of-tree 插件的新代码；排查前先确认进程启动时间与 `settings.yaml` 是否出现预期的运行时字段。
10. **刷新类 UI 必须有反馈和超时**：手动刷新必须显示请求/失败状态，Host 网络查询要设超时并写可见诊断；不能只依赖日志。
11. **参数 off 必须覆盖同维度的所有派生参数**：测试要覆盖 query 意图仍存在时的 off 组合。
12. **settings 驱动动作必须事件兜底**：Host 必须响应 `usageRefreshTick` 等运行时字段变化时，
    不能只依赖 `installSettingsSection` 的 `onChange`/`scope.watch`；应再注册
    `settings/updated` 事件监听，并用 tick 比较防重。

## 事故五：rc.7 keyed slot 使用旧版 id 注册导致设置卡片不出现

### 现象

升级到 DeepSeek Harness rc.7 后，设置页不再出现「搜索 Key 池」卡片，控制台报错：
`settings.plugin.item slot requires options.key`。

### 根因

rc.6 时代的 `ctx.slots.register({ name: 'settings.plugin.item', id: 'search-pool' })`
在 rc.7 已失效。rc.7 将 `settings.plugin.item` 从 list slot 改为 **keyed slot**：
注册必须使用 `key`，且 key 必须与 Host 的 Settings namespace 严格一致
（本项目为 `web-search-pool`），否则 slot 无法匹配导致卡片不渲染。

### 修复

```js
// ❌ rc.6 错误写法
ctx.slots.register({ name: "settings.plugin.item", id: "search-pool", order: 21 }, Card)

// ✅ rc.7 正确写法
ctx.slots.register({ name: "settings.plugin.item", key: "web-search-pool", order: 21 }, Card)
```

### 教训

1. rc.7 对 settings 插槽契约做了破坏性变更，升级前必须先核对官方 release notes 与本地
   源码中 slot 的注册约定。
2. keyed slot 的 key 必须与 Host Settings namespace 一致（本项目统一为 `web-search-pool`）。
3. 需要为 bundle 契约、client 契约、安装契约建立自动化测试，避免再次踩同类回归。

## 事故六：rc.7 中仍依赖 WEB_SETTINGS_NAMESPACES 白名单脚本

### 现象

rc.7 升级后仍运行 `scripts/patch-api-proxy-namespace.mjs`，脚本无法找到目标数组，DSH 启动异常。

### 根因

rc.7 的 `dsh-host-apiproxy` 不再使用旧版 `WEB_SETTINGS_NAMESPACES` 白名单机制：
已注册的 Settings namespace 会由设置代理直接暴露给浏览器。旧脚本属于 rc.6 时代的兼容手段，
不再是 rc.7 正常安装链路的一部分。

### 修复

1. 将脚本改为 rc.7 诊断模式：检测不到 `WEB_SETTINGS_NAMESPACES` 时输出提示并以成功退出。
2. 正常 rc.7 安装流程不再调用该脚本。
3. 通过 Bundle patch（`cordis.patch.yml`）原生接管 `web` row 的 `searchProvider`。

### 教训

1. DSH 版本升级时，先确认宿主机制的破坏性变更（如 settings 暴露方式、slot 契约、bundle 机制）。
2. 避免依赖安装目录 patch——优先使用官方 `cordis.patch.yml` Bundle 机制。
3. 所有机制结论需标注调研日期与本地源码来源，不凭印象写文档。
